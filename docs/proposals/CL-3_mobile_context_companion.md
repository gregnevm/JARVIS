## 0. TL;DR

APK перестає бути «ще одним чат-вікном» і стає **ambient-context компаньйоном**: на телефоні
збирає сигнали (сповіщення, дзвінки-метадані, SMS, використання), **редагує/фільтрує їх на
пристрої**, віддає **тільки на власний сервер користувача**, де локальний Ollama робить
summary та аналіз поведінки, і повертає **проактивні пропозиції дій у сповіщеннях**.

Чотири нові можливості (із запиту користувача):
1. **Щоденний контекст** → summary-логи дня.
2. **Логування + аналіз взаємодії зі сповіщеннями** (що читає / ігнорує / на що реагує).
3. **Summary дзвінків і переписок.**
4. **Пропозиції дій у сповіщеннях** на основі аналізу поведінки.

Плюс канал доставки самого APK — `/platform`-ендпоінт роздачі + QR-пейринг (із попередньої
ітерації), бо такий APK **не можна класти в Play Store** (обмежені дозволи) — лише
sideload/F-Droid, що ідеально лягає на суверенну роздачу зі штабу.

**Спинний принцип:** це найінвазивніша частина продукту. Прийнятна вона **лише** тому, що
весь потік даних = `телефон → твій сервер → локальний inference`, нуль третіх сторін (S1).
Це водночас і цінність, і єдина умова легальності.

**Зміна позиціонування (2026-06-16, рішення користувача):** APK — це не «ще один канал», а
**основний персональний клієнт = власне JARVIS**. Telegram **перестає бути primary** для
повсякденного персонального вжитку й рефокусується на соціальні/групові сценарії (див. розд. 1.5).
Це **суперечить наявному формулюванню S3 «Telegram — primary»** і вимагає поправки до статуту
(розд. 1.5 + IMPROVEMENT_PROPOSALS, за правилом самого `AGENTS.md`).

## 1. Чому це взагалі узгоджується з місією

| Принцип | Як цей фічер його дотримує |
|---------|----------------------------|
| **S1 Sovereignty** | Сирі сигнали йдуть **тільки** на self-hosted JARVIS; summary рахує локальний Ollama; жодного хмарного AI-API, жодної телеметрії третім сторонам. |
| **S2 Self-hosted ніколи не ламається** | Увесь ingest за прапором `ENABLE_MOBILE_INGEST=false`; кожне джерело — окремий toggle; Telegram-flow не зачеплено. |
| **S3 Канал ≠ мозок** | Телефон — лише **сенсор + редактор + батчер**. Summary/аналіз/пропозиції — у `tools`/`jarvis_core`, не на клієнті. |
| **S4 Human-in-the-loop** | Будь-яка *дія* з пропозиції виконується лише після тапу-підтвердження (computer-confirm CL-3.5). |
| **P1 Offline-first** | Збір працює офлайн, черга на пристрої, відправка при появі LAN/tunnel. |
| **P6 YAGNI** | Аналіз поведінки = лічильники/частоти, не важкий ML; ніякого on-device LLM (телефон слабкий, Ollama на хості). |

> ⚠️ **iOS неможливий за дизайном:** Apple не дає API до сповіщень/SMS/дзвінків інших застосунків.
> Цей фічер **Android-only за природою** — і це додатковий аргумент тримати фокус на APK (CL-3).

## 1.5 Позиціонування каналів: APK — це твій JARVIS

**Зрушення:** раніше — «Telegram primary, решта доганяє». Тепер — **у кожного каналу своя
окрема робота**, а персональний денний драйвер = APK.

| Канал | Роль ПІСЛЯ зсуву | Чому саме він |
|-------|------------------|---------------|
| **APK (Android)** | **Основний персональний клієнт = JARVIS** | єдиний, що вміє ambient-context (дзвінки/SMS/сповіщення), voice, push, проактивні пропозиції, computer-confirm з кишені. Telegram цього не вміє **в принципі**. |
| **Telegram** | **Соціальна/групова поверхня** (не daily-driver) | боти в групах (сім'я/команда), шеринг JARVIS іншим без інсталяції, швидкий доступ зсередини чужих розмов, і — критично — **єдиний клієнт для iOS** (де APK неможливий). |
| **Web `/platform`** | **Штаб** (адмін/консоль/налаштування) | без змін: керування, метрики, білінг, плани. |
| **`/v1` API** | Стовп A (розробник) | без змін. |

**Чому Telegram НЕ викидаємо, а рефокусуємо:**
1. **Групи/мультиюзер** — soціальний граф Telegram є цінністю, яку персональний клієнт не відтворює.
2. **iOS** — APK там неможливий → Telegram (+ web PWA) лишається єдиним JARVIS для iPhone.
3. **Zero-install reach** — поділитися ботом простіше, ніж змусити sideload-нути APK.

**Наслідок для S3:** принцип «бізнес-логіка не в каналі» лишається чинним для **всіх** клієнтів.
Змінюється лише **роль**: формулювання «Telegram — primary» → «APK — основний персональний клієнт;
Telegram — соціальний/груповий канал і iOS-fallback; Web — штаб». Пропонована поправка до
`AGENTS.md` S3 — у розд. 10 (D-5).

**Наслідок для пріоритетів roadmap:** замість «довести інші канали до Telegram-parity» —
**APK має дорости до лід-поверхні по персональних фічах**, а Telegram свідомо лишає собі лише
групове/соціальне/iOS. Поточна зрілість: Telegram 8/10, Mobile 0/10 → це **перехідний період**,
а не миттєве перемикання; Telegram працює як завжди, поки APK не догнав персональний UX.

## 2. Реалії Android (чесно про дозволи та межі)

Найважливіша частина: половина «очевидних» хотілок технічно обмежена ОС. Будуємо на тому, що
реально працює, і чесно позначаємо межі.

| Сигнал | Механізм Android | Дозвіл | Що РЕАЛЬНО доступно | Межа |
|--------|------------------|--------|---------------------|------|
| **Сповіщення** | `NotificationListenerService` | `BIND_NOTIFICATION_LISTENER_SERVICE` (grant у Settings) | пакет, заголовок, текст, час, **dismiss**; для наших власних нотифікацій — **tap** через PendingIntent | tap чужих нотифікацій напряму не ловиться; текст месенджерів обрізаний |
| **Дзвінки** | `CallLog` provider | `READ_CALL_LOG` | номер, ім'я, тип (in/out/missed), тривалість, час | **запис/транскрипт розмови заблоковано** на Android 10+ (треба бути default-dialer + InCallService, і навіть тоді віддалена сторона не пишеться на більшості OEM) |
| **SMS** | `SmsProvider` / receiver | `READ_SMS`/`RECEIVE_SMS` | повний текст SMS/MMS | Play-restricted (sideload OK) |
| **Месенджери** (WA/TG/Signal) | — | — | **лише дзеркало через NotificationListener** (частковий, ефемерний текст) | контент-API немає; Accessibility-скрейпінг — **відхиляємо** (крихкий, ToS/Play-порушення, проти духу S5) |
| **Використання застосунків** | `UsageStatsManager` | `PACKAGE_USAGE_STATS` (special access) | які застосунки, коли, скільки | агреговано, не вміст |
| **Календар / локація** (опц.) | Calendar/Location API | `READ_CALENDAR`, `ACCESS_*_LOCATION` | події, координати | строго opt-in, локацію тримати coarse |

**Висновок по «summary дзвінків і переписок»:**
- **SMS + дзеркало нотифікацій месенджерів** → summary реальний.
- **Дзвінки** → summary з **метаданих** (хто/коли/скільки/пропущені патерни) + опційний
  *пост-дзвінковий голосовий меморандум* користувача (диктовка → Whisper STT → summary).
  Автоматичний транскрипт живої розмови **не обіцяємо** — це чесна межа.

## 3. Архітектура: телефон-сенсор → сервер-мозок

```
 ┌──────────────────────── ANDROID APK (mobile/, сенсор+редактор+батчер) ────────────────────────┐
 │ Collectors:  NotificationListenerSvc · CallLogReader · SmsReader · UsageStats · (Calendar/Loc)  │
 │      ▼ on-device redaction (OTP/картки/користувацькі патерни) + per-source toggle               │
 │ Local encrypted queue (Room/SQLCipher) ── WorkManager batched upload (Wi-Fi/charging політика)  │
 └───────────────────────────────────────────┬─────────────────────────────────────────────────-─┘
        TLS (LAN / cloudflared tunnel), JWT   │  POST /api/v1/ingest/events   (idempotent, org-scoped)
                                              ▼
   gateway (8000)  — auth(JWT/initData) · rate-limit · org-resolve · → tools
                                              ▼
   tools (8200) / jarvis_core/  — redact-2 · normalize · → memory ; bg_jobs(daily) ; proposal-engine
        ├─► memory (8100)  device_events · daily_summaries · notif_interactions · behavior_profile
        │                  · action_proposals · (+ embed summaries у наявний pgvector RAG)
        ├─► Ollama (ХОСТ, Vulkan)  CHAT|AGENT — summary, аналіз, генерація пропозицій
        └─► push (FCM або UnifiedPush/ntfy)  ──►  actionable notification на APK
                                              ▲  tap «✅ Зробити» → computer-confirm (S4) → агент виконує
```

**Чому так:** телефон не тягне LLM; Ollama вже живе на хості (S1). Тож пристрій лише акумулює
й чистить, а вся інтелектуальна частина — у наявному агент-лупі (`tools/app/agent.py` +
`jarvis_core`), де вже є RAG-пам'ять і фонові джоби (`jarvis_core/bg_jobs.py`).

## 4. Бекенд: API, схема, джоби

### 4.1 Ingest API (новий, client-API, org-scoped, за прапором)

```
POST /api/v1/ingest/events     # батч типізованих подій; idempotent по client event_id (dedup)
GET  /api/v1/ingest/policy     # що сервер хоче збирати (per-source toggle, retention) — клієнт читає
POST /api/v1/context/purge     # one-tap видалення: raw / summaries / усе (за період)
GET  /api/v1/context/ledger    # «журнал прозорості»: що зібрано/відправлено/засумаризовано
```

Подія (приклад нормалізованого типу):
```json
{ "event_id":"<client-uuid>", "type":"notification|call|sms|usage",
  "ts":"<iso>", "source_app":"com.whatsapp", "payload":{...redacted...} }
```
Дисципліна: `event_id` клієнтський → ідемпотентність; ownership-перевірка + org-префікс
(`jarvis:{org_id}:…`) у Redis; rate-limit на ключ; **payload ніколи в логи** (у нас уже був
token-leak через httpx — той самий клас помилки).

### 4.2 Схема пам'яті (нові таблиці, Alembic-міграція)

| Таблиця | Призначення | Retention (дефолт) |
|---------|-------------|--------------------|
| `device_events` | сирі редаговані події, **партиціювання по днях** | короткий TTL (напр. 7–30 д), конфіг |
| `daily_summaries` | summary дня (+ embed у pgvector для RAG-continuity) | довгий / користувач керує |
| `notification_interactions` | агрегат: posted/dismissed/acted по app+типу | довгий |
| `behavior_profile` | вивчені патерни (частоти, вікна активності) | живе/оновлюване |
| `action_proposals` | згенеровані пропозиції + статус (offered/accepted/done/ignored) | середній |

> ⚠️ Embed-розмірність лишається `nomic-embed-text`=768D (жорстко в схемі) — summary
> ембедимо тією ж моделлю, без зміни розмірності (guardrail зі статуту).

> **Паспорт контексту (P9/P10/C1, [`DESIGN.md`](../DESIGN.md) §1.2.1):** кожна `device_event` і
> кожен `daily_summary` записується **не «голим»**, а з паспортом — `kind:` (`call`/`sms`/`notification`/`daily`),
> dense `summary`, namespaced-теги (`person:…`, `source:…`, `topic:…`, `sensitivity:…`) + embedding.
> Це не bespoke-рішення APK, а **екземпляр наскрізної культури**: ambient-дані індексуються й
> адресуються тими ж тегами, що й решта системи (звідси епізодичний пошук по життю, розд. 12.1,
> «безкоштовний» — він просто ретрив по паспортах). `sensitivity:`-тег керує redaction/vault.

### 4.3 Джоби та двигун пропозицій (`jarvis_core/bg_jobs.py`)

1. **Daily summary job** (cron, per-org): тягне події дня → друга редакція → агент-луп
   (CHAT/AGENT) робить summary → `daily_summaries` + embed → (опц.) push-дайджест.
2. **Behavior analysis** (інкрементально): рахує engage/ignore-rate по джерелах і часові вікна
   → оновлює `behavior_profile`. **Лічильники, не нейромережа** (P6).
3. **Proposal engine** (scheduled + подієвий): профіль + контекст → агент генерує кандидат-дії
   → ранжування → `action_proposals` → **actionable push** → тап → computer-confirm → виконання.
   Приклади: «Чернетка відповіді мамі?», «5 робочих листів проігноровано — звести?»,
   «Зустріч за 30 хв — вийти зараз».

## 5. Клієнт (APK) — компоненти

| Компонент | Технологія | Нотатка |
|-----------|-----------|---------|
| Оболонка | **TWA/WebView-wrap** над `/platform` PWA (CL-3.1 рекомендація) | найдешевший шлях; нативні мости лише там, де PWA не може |
| Collectors | `NotificationListenerService`, `CallLog`/`Sms`-reader, `UsageStats` | foreground service для лісенера; кожен — окремий екран-toggle |
| On-device redaction | regex-движок (OTP, картки, користувацькі правила) | **до** запису в чергу |
| Черга | Room + SQLCipher (encrypted-at-rest на пристрої) | переживає офлайн |
| Upload | WorkManager (batched, Wi-Fi/charging політика) | економія батареї |
| Push | **FCM** (зручно) **або UnifiedPush/ntfy** (суверенно, S1-чистіше) | ADR-рішення; ntfy можна self-host |
| Pairing | QR/deep-link `jarvis://pair?...` зі штабу | без перепідпису APK |

## 6. Приватність / безпека / закон (центральна вісь, не додаток)

- **Default OFF + гранулярний opt-in** на кожне джерело (S2/прапор-дисципліна). Нічого не
  збирається, поки користувач явно не ввімкнув конкретне джерело + не дав Android-дозвіл.
- **Дворівнева редакція:** на пристрої (before queue) і на сервері (before store). Видаляємо
  OTP/картки/секрети за патернами; патерни конфігуровані.
- **Retention + one-tap purge:** сирі події — короткий TTL; summary — за користувачем;
  `/context/purge` стирає за період/тип.
- **Журнал прозорості (`/context/ledger`):** користувач завжди бачить, що зібрано й відправлено.
- **Шифрування:** TLS у транзиті (LAN/tunnel), SQLCipher на пристрої; сервер — інфра користувача.
- **⚠️ Згода третіх сторін / GDPR:** summary чужих дзвінків/повідомлень торкається даних інших
  людей. Рятує **personal-use** виняток + те, що дані не покидають інфру користувача і не йдуть
  третім сторонам. Це **має бути задокументовано як guardrail** у `THREAT_MODEL.md`, а в застосунку —
  явний disclaimer при ввімкненні дзвінків/SMS.
- **Play Store:** обмежені дозволи (`READ_SMS`, `READ_CALL_LOG`, notification-listener) → **тільки
  sideload/F-Droid**. Синергія: саме тому потрібен ендпоінт роздачі APK зі штабу (розд. 7).

## 7. Канал доставки APK (з попередньої ітерації, лишається)

Generic підписаний APK + рантайм-конфіг через QR/deep-link (без перепідпису на льоту).

```
GET  /platform/api/apk/info   → {version, size, sha256, source, available}
GET  /platform/apk            → стрім APK (auth-gated, mime vnd.android.package-archive)
POST /platform/api/apk/pair   → one-time pairing-токен (Redis, org-префікс, TTL) → {deeplink}
GET  /platform/api/apk/qr     → QR для deep-link
```
Новий модуль `gateway/app/platform/apk.py` із `register(router)` + таб у `platform.html`.
Сорсинг артефакту: GH-Release → кеш `data/clients/jarvis-<ver>.apk` (sha256-verify), фолбек
`503 not_available` офлайн без кешу.

## 11. Свідомо НЕ робимо

- ❌ **On-device LLM** — телефон слабкий, Ollama на хості (S1/P6).
- ❌ **Accessibility-скрейпінг месенджерів** — крихко, ToS/Play-порушення, проти духу tier-ladder.
- ❌ **Автотранскрипт живих дзвінків** — ОС блокує; не обіцяємо.
- ❌ **Будь-яка відправка даних кудись, крім сервера користувача** — ламає S1, вся суть фічера.
- ❌ **Збір без явного per-source opt-in** — default OFF завжди.
- ❌ **Auto-виконання пропозицій** — лише після тапу-підтвердження (S4).
- ❌ **iOS-паритет** — неможливо технічно; Android-only.

## 12. Додаткові покращення (беклог ідей, не committed)

Ранжовано за «цінність × узгодженість зі стеком». ★ = раджу взяти в CL-3 одразу.

### Інтелект і якість контексту
- ★ **Edge-тріаж на пристрої** — крихітний класифікатор/правила (TFLite, не LLM) вирішує
  *чи варто подію взагалі вивантажувати*. **Менше даних покидає телефон = приватніше + менше
  батареї/навантаження на сервер.** Нюанс vs «no on-device LLM»: це не інференс LLM, а легкий
  фільтр важливості (P6-сумісно). Узгоджує S1 ще сильніше.
- ★ **People-centric контекст (entity resolution)** — звести одну людину крізь джерела
  (номер ↔ контакт ↔ messenger-нік) у «граф людей». Summary стає про людину, а не про джерело:
  *«Сьогодні з мамою: 2 дзвінки, 5 повідомлень, питає про X»*. Великий стрибок якості summary.
- **Сенсорний контекст подій** — корелювати сигнали в часі (пропущений дзвінок → відразу SMS
  «передзвони») у єдиний наратив, а не розрізнені рядки.

### Довіра, приватність, UX
- ★ **Контекст-залежний тайминг пропозицій** — не пінгувати під час зустрічі / о 3-й ночі;
  quiet-hours + вивчені вікна активності (з `behavior_profile`). Plus **«пауза-паніка»**
  (одним тапом стоп усього збору) і **гео-пауза** (нічого не збирати біля клініки/за геозоною).
- **Рівні чутливості + локальний vault** — категорії «здоров'я/фінанси» **ніколи не вивантажують
  сире**, лише derived-summary з вирізаним PII. Tiered sensitivity поверх per-source toggle.
- **Підписаний tamper-evident ledger + consent-receipts** — журнал прозорості з підписом
  (не підробити заднім числом) і фіксація стану згоди — конкретна відповідь на GDPR/третю сторону.

### Суверенне розповсюдження (розширює розд. 7)
- ★ **Self-update канал** — APK не в Play Store, тож сам перевіряє `/platform/api/apk/info` на
  нову версію → нотифікація → завантаження. Ендпоінт роздачі це вже дозволяє, треба лише update-check.
- **TLS/pubkey-pinning до ВЛАСНОГО сервера** — self-hosted часто self-signed/tunnel; клієнт пінить
  ключ сервера користувача (захист від MITM на LAN/tunnel). + **reproducible APK build** для перевірки.

### Голос (переюз наявного `tts/` piper UA + whisper)
- ★ **Voice-first quick-capture** — диктовка з шторки/quick-tile → Whisper → memory. Найнижче трення вводу.
- **Озвучений ранковий/вечірній брифінг** — TTS-дайджест дня українським голосом (`tts/` вже є):
  *«Доброго ранку, ось що важливо сьогодні»*. Нульова нова інфраструктура.

### Крос-стовпова синергія
- ★ **Апрув coding-агента (Стовп B) з телефона** — JARVIS дописав рефактор/прогнав тести → push
  *«Готово, підтвердити diff?»* → review+confirm у кишені (computer-confirm CL-3.5). Зв'язує
  ambient-компаньйон зі Стовпом B — одна поверхня апруву для всього.
- **Корекційний цикл → LoRA (Twin/Edge)** — користувач править невдалий summary → правка стає
  локальним train-сигналом через наявний `twin/` (ModelRegistry · LoRA sync · Edge ingest, див.
  [`DESIGN.md`](../DESIGN.md)). **Суверенний само-апгрейд: твої дані тренують твою ж модель локально.**

### Інженерна стійкість
- ★ **Версіонування схеми подій** (`event_schema_version`) — мобільний клієнт оновлюється повільно;
  колектори й сервер мають еволюціонувати незалежно.
- **Resumable cursor-sync, толерантний до clock-skew** — чекпойнт-курсор замість «останні N»;
  годинник телефона ненадійний (серверний час — авторитет).

## 12.1 Друга хвиля ідей

Те, що перетворює зібраний контекст із «логів» на **активного асистента життя**. Переюзає наявні
моделі (VISION/EMBED/LoRA) і сервіси (`tts/`, `whisper/`).

### Контекст як пам'ять (переюз pgvector RAG)
- ★ **Епізодичний пошук по життю** — *«що я обговорював з Х минулого місяця»*, *«де я був, коли
  дзвонив банк»* — семантичний + часовий запит по ambient-корпусу. **Це і є сенс збору даних:
  твоє життя стає queryable.** Нуль нової інфри — наявний `/search` + часовий фільтр.
- ★ **Трекінг обіцянок / open loops** — витягати зобов'язання («передзвоню», «нагадай», «зроблю»)
  зі своїх і чужих повідомлень → відстежувати незакриті → нагадувати. Перетворює потік на
  персональну систему підзвітності.
- **Нагадування про занедбані зв'язки (people-graph)** — *«не відповідав мамі 5 днів»*,
  *«не дзвонив другу 2 міс»*. М'яко, opt-in.

### Проактив, що реально корисний
- ★ **Чернетки відповідей у твоєму стилі** — генерувати draft-відповіді стилем користувача
  (вивченим зі своїх надісланих SMS) → у сповіщенні → тап-відправити (з confirm). Топ повсякденної
  цінності; синергія з корекція→LoRA.
- ★ **Локальний scam/phishing-щит** — детект шахрайських патернів у SMS/дзвінках (невідомий
  повторний дзвонар, фішинг-лінк) **повністю локально**. Диференціація: хмарні застосунки заради
  цього відсилають твої SMS назовні — JARVIS ні (S1).
- **Гео-залежні пропозиції** — geofence + нотатки/список: *«ти біля магазину — у списку молоко»* (opt-in локація).

### Багатша модальність (переюз VISION-моделі)
- ★ **Візуальний capture** — поділитися скріншотом/фото/чеком → Ollama VISION витягує контекст →
  memory/нотатки (*«нотатка з цього чека»*, OCR інфо зі скрінів). Модель VISION уже в стеку.

### Стійкість і контроль
- **Degraded offline-summary** — сервер недоступний довго → структурований **не-LLM** дайджест на
  пристрої, що догенерується при поверненні сервера. Чесний P1 offline-first.
- ★ **Per-contact include/exclude** — ніколи не інджестити нічого, прив'язаного до певних
  людей/номерів (терапевт, юрист, ex). Гранулярний guardrail довіри поверх per-source toggle.

### Нова роль Telegram (соціальний канал)
- **Груповий дайджест** — JARVIS у сімейній/командній групі: summary розмови + action-items +
  спільні нагадування. Дає рефокусованому Telegram (розд. 1.5) **реальну власну роботу**, а не
  лишки від персонального клієнта.
