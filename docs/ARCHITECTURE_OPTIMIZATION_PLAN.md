# JARVIS — Architecture Optimization Plan (трек AO)

> **Статус:** PLAN (жоден пункт ще не реалізований — чекбокси нижче і є SSOT статусу).
> **Версія:** 1.0 (2026-07-02)
> **Місце:** трек-roadmap оптимізації рантайму й вартості. Не додає нових фіч-стовпів —
> зміцнює фундамент під усіма трьома (𝗔/𝗕/𝗖, [`AGENTS.md`](../AGENTS.md) §2) та ріже
> вартість токенів/уваги. Дружить з [`DESIGN.md`](DESIGN.md) (ADR) і
> [`CONTEXT_MODULE.md`](CONTEXT_MODULE.md) (Context Kernel — це його v2).
> **Походження:** шість ідей із зовнішнього аудиту архітектури (workflow-JIT, context-GC,
> KV-картриджі, мовний арбітраж, record-replay, headless/agent-first), приземлені на
> реальні модулі репо.

---

## 0. Одне речення

**Мета треку:** модель виходить із циклів, де рішення вже ухвалене (Reflex), контекст
живе поколіннями з TTL (Kernel v2), важкі префікси гріються один раз (KV-картриджі),
внутрішні обміни дешевшають (EN/JSON між агентами), кожен ран відтворюваний (trace),
а інструменти JARVIS доступні будь-якому клієнту через один MCP-шар.

**Дві ІКР-метрики треку** (у дашборд `data/autopilot/dashboard.md` + kaizen meta-OKR):

| Метрика | Зараз | Ціль |
|---------|-------|------|
| `model_calls/task` — LLM-викликів на повторювану задачу | 1+ завжди | → 0 для задач із Reflex-хітом |
| Хвилини уваги CEO/день на рутину | не міряємо | міряємо → ↓ |

## 1. Мапа: ідея з аудиту → реальний якір у репо

Назви з аудиту («Meta-Orchestrator», «DAG Execution Layer», «AAA Resource Adapter
Layer») — концептуальні. У коді їм відповідають:

| # | Ідея (аудит) | Назва з аудиту | Реальний якір у репо | Стан якоря |
|---|--------------|----------------|----------------------|-----------|
| AO-1 | Workflow JIT | «Meta-Orchestrator + Reflex Layer» | `tools/app/macros.py` (іменовані PS/CLI без LLM) · `tools/app/computer_learned.py` (авто-whitelist після confirm) · `tools/app/orchestrator.py` (Orchestrator+Critic) | зародок є: macros = ручний Reflex, learned = механізм promotion |
| AO-2 | Context GC | «Context Kernel v2» | [`CONTEXT_MODULE.md`](CONTEXT_MODULE.md) конвеєр · `jarvis_core/passport/` · `memory` (pgvector, `context_events`) · bg-джоба `context_retention` | v1 задизайнений, частково реалізований |
| AO-3 | KV-картриджі | «Twin-нода, llama.cpp» | `edge/` (KoboldCPP, ADR-001) · `edge/personas/` · `twin` ModelRegistry | рантайм є, прогрівання KV нема |
| AO-4 | Мовний арбітраж | «Міжагентний протокол» | `ORCHESTRATOR_SYSTEM`/`CRITIC_SYSTEM` у `tools/app/orchestrator.py` (зараз UA!) · внутрішні промпти `jarvis_core/llm` | всі внутрішні обміни платять UA-податок токенізатора |
| AO-5 | Record-replay | «DAG Execution Layer, event-sourced trace» | `jarvis_core/llm/jsonl_log.py` (SSOT append-only, DESIGN §6.1) · session-логи · `tools/app/dataset_export.py` (ShareGPT) · `data/logs/computer.jsonl` | лог є, але без input-hash/seed/params → replay неможливий |
| AO-6 | Headless-first | «AAA Resource Adapter Layer → MCP» | `tools/app/mcp_gateway.py` — **лише клієнт** (JARVIS кличе зовнішні MCP) · `/v1` OpenAI-surface | бракує дзеркальної половини: JARVIS як MCP-**сервер** |

## 2. Трек-задачі

### AO-1 · Reflex Layer — модель виходить із повторюваних циклів

**Ідея:** третє повторення тієї самої задачі — сигнал, що рішення вже ухвалене і
модель у циклі зайва. Компілюємо hot path у детермінований скрипт.

**Механіка (розширює macros, не замінює):**
1. **Сигнатура задачі** — hash(нормалізований intent + набір викликаних tool-ів).
   Лічильник повторів у Redis: `jarvis:{org_id}:reflex:sig:{hash}` (org-префікс —
   статут §5).
2. **3-тє повторення** → bg-джоба `reflex_codegen`: coder-модель
   (`qwen2.5-coder:14b`) генерує скрипт у `data/reflex/{sig}.py|.ps1`.
3. **Shadow-run:** скрипт ганяється **поряд** із модельним шляхом, результати
   порівнюються по trace (потребує AO-5!). Розбіжність → скрипт у карантин.
4. **Promotion:** N збігів підряд (дефолт 3) → скрипт стає macro (реєстр
   `macros.py`), модель виходить із циклу. Механізм promotion уже відпрацьований
   у `computer_learned.py` — та сама модель довіри.

**Safety-інваріанти:** promoted-скрипт проходить ту саму confirm-політику, що й
macro (S4 незмінний); Reflex — це фактично новий щабель **нижче T0** у tier ladder
(S5): «взагалі без моделі — пряміше за пряме».

- [ ] AO-1.1 Сигнатура задачі + Redis-лічильник повторів
- [ ] AO-1.2 bg-джоба `reflex_codegen` (за прапором `ENABLE_REFLEX=false`)
- [ ] AO-1.3 Shadow-run + компаратор по trace (залежить від AO-5.1)
- [ ] AO-1.4 Promotion у macros + demotion при першій розбіжності
- [ ] AO-1.5 Метрика `model_calls/task` і reflex hit-rate у дашборд

**Метрика:** `model_calls/task → 0` для задач із Reflex-хітом.

### AO-2 · Context Kernel v2 — покоління та TTL

**Ідея:** контекст — як GC-heap: young generation одноразовий, у durable потрапляє
лише те, що явно закомічено.

**Покоління (лягають на існуючий конвеєр CONTEXT_MODULE):**

| Покоління | Що це | Де живе | TTL |
|-----------|-------|---------|-----|
| **L0** | робоче вікно агент-лупу | пам'ять процесу / Redis-сесія | до кінця task |
| **L1** | session summary (Δ-report при закритті сесії) | session-логи → паспорт | дні; клас факту вирішує |
| **L2** | durable-паспорти | `context_events` (pgvector) | по класу факту (`context_retention`) |

**Що додати понад v1:**
- TTL **по класу факту** (namespaced-тег `ttl:*` або поле паспорта), а не один
  глобальний retention.
- **Токен-бюджети на підсистему** при збиранні промпта (agent-RAG InputDecorator):
  скільки токенів максимум дає RAG, скільки — reminders, скільки — persona.
  Явний бюджет = P3 (Explicit over Implicit).
- Дисципліна «все, що має пережити сесію, комітиться явно» — L1→L2 promotion
  тільки через паспорт (C1 вже це вимагає; бракує самого кроку Δ-report).

- [ ] AO-2.1 Класи TTL у паспорті + retention по класу
- [ ] AO-2.2 Токен-бюджети підсистем в InputDecorator (конфіг, не хардкод)
- [ ] AO-2.3 Δ-report при закритті сесії → L1-паспорт (fast path, без LLM де можливо)
- [ ] AO-2.4 Метрики: токени/хід (по підсистемах) + hit-rate L2 у ретриві

**Метрика:** токени/хід ↓, hit-rate L2 ↑.

### AO-3 · KV-картриджі — warm boot для Edge

**Ідея:** системний промпт + persona + база знань — стабільний префікс. Токенізувати
його щоразу — податок; KV-стан кешується на диск і вантажиться при старті.

**Якір:** Edge = KoboldCPP (ADR-001, llama.cpp-сімейство). Дослідити:
context-shifting/fast-forwarding у KoboldCPP vs `--prompt-cache` save/load у
чистому llama.cpp. Якщо KoboldCPP не вміє персистити KV на диск — це **датований
констрейнт ADR-001** (див. §3), і експеримент із llama.cpp-server як альтернативним
engine у `edge/engines/` — легітимний.

- [ ] AO-3.1 Спайк: KV-персист у KoboldCPP (наявний engine) — так/ні
- [ ] AO-3.2 Якщо ні: llama.cpp `--prompt-cache` прототип, `run_win.bat`/`run_linux.sh`
      гріють картридж при старті
- [ ] AO-3.3 Картридж = артефакт Twin-синку (persona+знання версіонуються ModelRegistry)
- [ ] AO-3.4 Метрика TTFT після рестарту (до/після)

**Метрика:** TTFT після рестарту ↓ на порядок.

### AO-4 · Мовний арбітраж — UA лише на людській межі

**Ідея:** українська платить 2.2–2.7× токенів проти англійської на тому самому
змісті. Люди отримують UA; агенти між собою — EN або компактний JSON.

**Конкретні цілі в коді:**
- `ORCHESTRATOR_SYSTEM` / `CRITIC_SYSTEM` (`tools/app/orchestrator.py`) — зараз UA,
  а це суто внутрішній обмін Orchestrator↔Worker↔Critic. Critic і так відповідає
  JSON — лишилося перевести інструкції та план на EN.
- Внутрішні службові промпти `jarvis_core` (summarize, passport, routing) — EN;
  **поле `summary` паспорта лишається UA** (його читає людина в Platform).
- Правило в статут-стилі: *UA — на межах Telegram/TTS/Platform-UI; EN/JSON — усередині.*

**Ризик:** якість локальних моделей на EN-інструкціях ≠ на UA — не припускаємо,
міряємо (A/B на наявних eval-сценаріях перед мерджем кожного промпта).

- [ ] AO-4.1 Інвентаризація внутрішніх промптів (grep по системних константах)
- [ ] AO-4.2 Orchestrator/Critic → EN + A/B eval
- [ ] AO-4.3 Службові промпти jarvis_core → EN + A/B eval
- [ ] AO-4.4 Метрика: токени на внутрішній обмін (до/після)

**Метрика:** вартість/дзвінок внутрішніх обмінів ↓ ~2×.

### AO-5 · Record-replay — event-sourced trace агент-лупу

**Ідея:** «вчорашній фейл» має відтворюватися. Лог уже є (`jsonl_log.py` — SSOT,
«сирі сесії = джерело для training-датасетів»); бракує полів для replay.

**Схема запису (розширення, append-only контракт не ламається):**
`node` (крок лупу) · `input_hash` · `tool_result` (або hash + blob-ref) · `seed` ·
sampling-params · версія моделі з ModelRegistry (P7 — реєстр і є авторитет версій).

**Replay-режим:** pinned tool-outputs із trace + фіксований seed → детермінований
повтор рану без побічних ефектів (інструменти не викликаються — відповіді
підставляються з логу).

**Бонус (безкоштовний):** цей самий trace — готовий датасет для QLoRA-пайплайну:
`dataset_export.py` уже вміє ShareGPT; додаткові поля його лише збагачують
(`training/`, Twin Етап C/D у GAP_ANALYSIS).

- [ ] AO-5.1 Розширена схема запису в агент-лупі (`jarvis_core/agent/tool_loop.py`)
- [ ] AO-5.2 Replay-раннер: `jarvis replay <session>` (CLI у `tools/app/cli.py`)
- [ ] AO-5.3 `dataset_export` підхоплює нові поля (фільтр якості по збігу replay)
- [ ] AO-5.4 Метрика: % відтворюваних ранів

**Метрика:** % ранів, що реплеяться біт-у-біт (ціль ≥ 90% для tool-детермінованих).

### AO-6 · JARVIS як MCP-сервер — один шар адаптерів на всі клієнти

**Ідея:** `mcp_gateway.py` — це вхідна половина (JARVIS **споживає** MCP). Дзеркальна
половина — JARVIS **надає** свої інструменти як MCP-сервер, і тоді Claude Code /
Claude.ai / будь-який MCP-клієнт користуються тим самим адаптерним шаром, що й
Telegram. Telegram стає просто ще однією проєкцією. Це найбільший стратегічний
рядок треку: Edge/Twin перестає бути закритою системою.

**Контури:**
- Транспорт: stdio (локальний Claude Code) + streamable HTTP (віддалені клієнти)
  на `tools` або окремим роутером у gateway (I/O — у gateway, мозок у tools; S3).
- Auth: наявні API-ключі Стовпа A (`Bearer sk-jarvis-…`), scopes на інструменти.
- Експонуються **ті самі** tool-схеми, що бачить внутрішній агент-луп (P7: одна
  схема — одне місце).
- **Прапор** `ENABLE_MCP_SERVER=false` (дефолт безпечний) + **оновлення
  THREAT_MODEL обов'язкове** — прецедент P5.3: MCP без threat model не мерджиться.
- Confirm-політика S4 діє й для зовнішніх MCP-викликів: мутуючі дії з Claude Code
  проходять ту саму confirm-чергу, що з Telegram.

- [ ] AO-6.1 ADR: транспорт/розміщення MCP-сервера (tools vs gateway)
- [ ] AO-6.2 MVP: read-only інструменти (recall_notes, context retrieve, status)
- [ ] AO-6.3 Мутуючі інструменти через confirm-чергу + THREAT_MODEL update
- [ ] AO-6.4 Клієнтська перевірка: Claude Code бачить JARVIS-інструменти end-to-end

**Метрика:** 1 шар адаптерів обслуговує N клієнтів (Telegram, Platform, APK, MCP).

## 3. Методика: аудит скам'янілих констрейнтів (квартальний ритуал)

Кожен ADR у [`DESIGN.md`](DESIGN.md) §11 ухвалювався під конкретний констрейнт
(залізо, версія бібліотеки, брак часу). Констрейнти вмирають тихо — рішення
залишаються. Ритуал:

1. **Датуй констрейнт** кожного ADR: одне речення «це рішення живе, поки правда X»
   (напр. ADR-E2 «Ollama не в Docker» живе, поки хост = AMD/Windows без `/dev/kfd`;
   ADR-001 KoboldCPP — поки не потрібен KV-персист, див. AO-3).
2. **Раз на квартал** пройди список: X ще правда? Мертвий констрейнт = кандидат
   на зріз (новий ADR, що supersede-ить старий).
3. Знахідки — у `docs/IMPROVEMENT_PROPOSALS.md`, як велить D1.

## 4. Порядок виконання (залежності)

```
AO-2 (Kernel v2) ──► AO-5 (trace) ──► AO-1 (Reflex: shadow-run порівнює по trace)
AO-4 (мовний арбітраж)  — незалежний, дешевий, будь-коли
AO-3 (KV-картриджі)     — незалежний спайк на Edge
AO-6 (MCP-сервер)       — незалежний; ADR перший, MVP read-only другий
AO-7 (аудит ADR)        — ритуал, стартує одразу
```

Рекомендована черга: **AO-4 + AO-7** (free lunch, нуль ризику) → **AO-2 → AO-5 →
AO-1** (основний ланцюг) → **AO-6** паралельно з місячним горизонтом → **AO-3**
як спайк між ітераціями.

## 5. Свідомо НЕ робимо (межі треку)

- ❌ **Переписувати агент-луп під DAG-фреймворк** (LangGraph тощо) заради trace —
  guardrail статуту вже забороняє; AO-5 додає поля в існуючий JSONL, не двигун.
- ❌ **Reflex без shadow-run** — «модель написала скрипт, одразу в прод» ламає S4;
  promotion лише через збіги з модельним шляхом.
- ❌ **MCP-сервер без прапора і threat model** — прецедент P5.3 обов'язковий.
- ❌ **EN у людських відповідях** — арбітраж стосується лише внутрішніх обмінів;
  Telegram/TTS/UI лишаються UA.
- ❌ **Зміна embed-моделі під Kernel v2** — 768D жорстко (guardrail статуту).
- ❌ **Глобальний «розумний» GC контексту LLM-ом** — retention по класу факту,
  детерміновано (P6: не будуємо ML там, де вистачає TTL).

## 6. Дотичне до самого репо (з того ж аудиту, поза треком AO)

Два пункти аудиту стосуються не рантайму JARVIS, а робочого середовища цього репо:

- **Токен-лінт скілів:** тіла `.claude/skills/kaizen/*` написані UA і платять той
  самий податок токенізатора при кожному завантаженні скіла. Рефактор: `description`
  двомовний (тригери UA лишаються), тіло — EN. Окремий дрібний PR.
- **CLAUDE.md як компільований контекст:** репо має `AGENTS.md` (статут), але Claude
  Code читає `CLAUDE.md`. Тонкий `CLAUDE.md` → «читай AGENTS.md першим» закриває
  розрив без дублювання (P7: один факт — одне місце).
